How Pheme works

Lightweight in-process messaging for .NET: commands and queries with one handler each, an ordered pipeline of behaviors, domain events published when Entity Framework Core saves, and integration events delivered through an outbox. This page shows what happens at each step; the documentation has the details.

Messages travel. Pheme carries the word.

1What Pheme does

Pheme moves messages inside one application. Each kind of message has its own rules, and every rule that can be checked is checked when the application starts, not on the first request.

Commands and queries

Sent through ISender to exactly one handler. A command changes state, a query reads it.

Pipeline behaviors

Cross-cutting code around every message, in the order it was added: authorization, transactions, caching.

Validation

FluentValidation as a ready-made behavior; validators are found next to the handlers.

Request logging

One log per message with its outcome and time; expected failures without a stack trace.

Domain events

Published when a DbContext saves, before it writes, so the handlers' changes join the same transaction.

Integration events

Written to an outbox table with the change, delivered after the commit, at least once, with retries and parking.

Testing helpers

Deliver the outbox when a test says so, read and redeliver events, check layers in architecture tests.

Tracing and metrics

A span and a duration for every message, event and delivery, through System.Diagnostics.

No reflection per call, no source generators, internal handlers welcome. The domain never references Pheme: domain events are the application's own types.

2Registration and the start-up check

Pheme is registered with AddPheme, naming the assemblies that hold the handlers. In a modular monolith each module registers its own handlers from its infrastructure, and the composition root adds what all modules share - the pipeline, the outbox and the contracts:

// Ordering.Infrastructure, in the module's registration
services.AddPheme(pheme => pheme.AddHandlersFromAssemblyContaining<OrderingModule>());

// Shop.Api: the modules, then the pipeline
builder.Services.AddOrdering(connectionString);
builder.Services.AddShipping(connectionString);
builder.Services.AddPheme(options => options
    .AddHandlersFromAssemblyContaining<OrderPlacedIntegrationEvent>()   // the contracts
    .AddOutbox()
    .AddRequestLogging()
    .AddFluentValidation());
  • Calls add up. Every call shares one registry and one pipeline, in call order; an assembly is scanned once.
  • Scanning finds concrete handler classes, internal and nested ones too, in the order of their full names, and registers them as transient, so a handler may depend on a scoped DbContext. A handler registered by hand before AddPheme keeps its registration.
  • Assemblies are named explicitly, never discovered: AppDomain knows only the assemblies loaded so far.

What fails the start

When the host starts - or, without a host, when ISender is first resolved - every configuration error is reported in one OptionsValidationException, one line per problem:

  • a message without a handler (with the assemblies searched), with two handlers, or implementing two of ICommand, ICommand<T>, IQuery<T>;
  • a behavior registered as the interface instead of through AddBehavior;
  • a domain event handler that can never run (of an interface or abstract event type);
  • a DbContext that collects domain events but whose options are not scoped (pooling, a singleton factory);
  • outbox mistakes: integration event handlers without AddOutbox, an outbox without a store, UseOutbox without AddOutbox, one module or source in two contexts, an integration event without a handler, an event type that cannot be delivered.

3Sending a message

public sealed record PlaceOrderCommand(string Product, int Quantity) : ICommand<Guid>;

internal sealed class PlaceOrderCommandHandler(IOrderingDbContext db) : ICommandHandler<PlaceOrderCommand, Guid>
{
    public async Task<Guid> Handle(PlaceOrderCommand command, CancellationToken cancellationToken)
    {
        Order order = Order.Place(command.Product, command.Quantity);
        db.Orders.Add(order);
        await db.SaveChangesAsync(cancellationToken);
        return order.Id;
    }
}

Guid id = await sender.Send(new PlaceOrderCommand("Lamp", 2), cancellationToken);
  • Scoped sender. ISender belongs to a scope, so handlers get the request's DbContext. A singleton that depends on it fails scope validation instead of silently using the root provider; code outside a request creates a scope first.
  • Exceptions reach the caller unchanged - never a TargetInvocationException or an AggregateException.
  • Task, not ValueTask, and no Async suffix: Send, Publish, Handle.

4Pipeline behaviors

A behavior wraps the handling of every message its generic constraints accept: ICommand, ICommand<TResponse>, IQuery<TResponse>, IMessage for all, or a marker interface of the application. It is added as an open generic type and closed for each message that fits.

options.AddRequestLogging(logging => logging.IsExpected = e => e is ValidationException);   // always outermost
options.AddBehavior(typeof(AuthorizationBehavior<,>));
options.AddBehavior(typeof(CommandTimingBehavior<>));      // commands without a response
options.AddBehavior(typeof(CommandTimingBehavior<,>));     // commands with one
options.AddFluentValidation();                             // validates here, in order
options.AddBehavior(typeof(TransactionBehavior<>));

Ready-made behaviors

  • Validation (Pheme.FluentValidation) runs the validators of a message one after another - they often share a scoped DbContext - and throws all failures together, as FluentValidation's exception or the application's own, made by a factory.
  • Request logging writes one log per message in the category Pheme.Requests: handled on Debug, an expected failure (IsExpected, or cancellation) on Information with its message, anything else on Error with the exception. Off until AddRequestLogging is called.

Recipes, each with a use case in the example: transactions · authorization · caching queries · idempotent commands · audit trail

5Domain events, published on save

Domain events are the application's types; entities collect them the way the application likes - a base class or an interface of its own domain. Pheme is told, per DbContext, how to read and clear them:

services.AddPhemeDbContext<ShippingDbContext>(pheme =>
    pheme.CollectDomainEventsFrom<AggregateRoot>(
        entity => entity.DomainEvents,           // the events not published yet, in order
        entity => entity.ClearDomainEvents()));  // forgets them, right before they are published

services.AddDbContext<ShippingDbContext>(options => options.UseNpgsql(connectionString));

An EF Core interceptor - no base DbContext - then publishes the events whenever the context saves. Handlers implement IDomainEventHandler<TEvent>, any number per event, and only change entities; the save that published the event stores their changes.

Dispatch rules

  • Exact type. An event reaches the handlers of its runtime type only. For every event of a kind, such as auditing, register an open generic handler by hand.
  • In order. Handlers registered by hand before AddPheme first, then the scanned ones by full type name.
  • The first exception stops the remaining handlers and events, and the save does not happen.
  • One transaction covers one DbContext. A handler that changes another module's context writes in another transaction - between modules, use integration events.
  • No saving from inside. A handler that saves the context publishing its event throws: that save would commit part of the change on its own. A synchronous SaveChanges with events pending throws too.

A domain event handler runs before the save, which may still fail. An e-mail or a call to another system belongs to an integration event, delivered after the commit.

6Integration events and the outbox

An integration event (IIntegrationEvent) is written to the outbox table of its module in the same transaction as the change that raised it, and delivered later, in the background, to its IIntegrationEventHandler<TEvent> handlers. If the save fails, the event was never written; once it succeeds, the event will be delivered.

// OnModelCreating of the module's DbContext
modelBuilder.AddPhemeOutbox();                       // table outbox_messages in the default schema

// infrastructure of the module
services.AddPhemeDbContext<OrderingDbContext>(pheme => pheme.UseOutbox<OrderingModule>());

// a handler in the application layer - it never sees the DbContext
outbox.Add(new OrderPlacedIntegrationEvent(Guid.CreateVersion7(), timeProvider.GetUtcNow(), order.Id));

Retries with a growing delay

A failed message waits RetryDelay (10 s), twice as long after each further failure, at most MaxRetryDelay (15 min). After MaxAttempts (10) failed attempts - about 50 minutes of failures with the defaults - it is parked. A short outage of a mail server is outlasted, and a message that keeps failing does not hold up the others: a message is not read again before its due time.

Layouts and guarantees

  • One outbox per DbContext. A context per module, each with its own table; modules sharing one context, each with its own writer; or an application without modules. A writer writes only to its own context - another one would be another transaction.
  • The stored name is [IntegrationEventName("ordering.order-placed")], or else the full type name; the content is JSON with the web defaults. Additive changes are safe; a breaking change is a new type with a new name.
  • An event without a handler fails the start when its assembly is scanned, and otherwise throws from Add - the outbox would only park it.
  • Operating it: IOutboxMaintenance lists and requeues parked messages; AddPhemeOutboxCheck is Degraded while the oldest pending message is older than 5 minutes and Unhealthy while one is parked - wire it to alerts, not to the host's probes.
  • One instance. The stores do not lock rows: run the processor in one instance of the application. PostgreSQL only.

8Testing

Handlers are plain classes, unit tested without Pheme. Integration tests run the whole application against a real database, and Pheme.Testing makes the outbox deterministic:

  1. Deliver only when the test says so. UsePhemeOutboxForTests() turns the processor off and retries failed messages at once.
  2. Send, drain, assert. DrainOutbox() delivers until nothing is left, events the handlers wrote included, and throws for a failed message with its error.
  3. Read what was written. GetOutboxEvents<TEvent>() returns the events saved in the outbox, in the order they occurred.
  4. Prove idempotency. Redeliver<TEvent>(predicate) makes processed events pending again, so the next drain calls all their handlers once more.
Guid orderId = await client.PlaceOrder();
Assert.Single(await factory.Services.GetOutboxEvents<OrderPlacedIntegrationEvent>(), e => e.OrderId == orderId);

await factory.Services.DrainOutbox();
Assert.Equal(ShipmentStatus.Preparing, (await FindShipment(orderId))?.Status);

10Configuration

Pheme does not read IConfiguration itself: every option is a property of an options class, set in code, and bound from appsettings.json or an environment variable by the application, under a section name of its choice. Properties not set keep their defaults; a wrong value throws when the section is bound, and changes need a restart.

options.AddOutbox(outbox => builder.Configuration.GetSection("Outbox").Bind(outbox));
options.AddRequestLogging(logging => builder.Configuration.GetSection("RequestLogging").Bind(logging));

11Limitations

  • Registrations are validated from the IServiceCollection; handlers registered only in a third-party container are reported as missing.
  • Handler wrappers are cached per message type for the life of the process, which keeps types of collectible AssemblyLoadContexts alive.
  • The outbox of Pheme.EntityFrameworkCore supports PostgreSQL only, and its processor runs in one instance of the application. Storage other than EF Core can implement IOutboxStore.
